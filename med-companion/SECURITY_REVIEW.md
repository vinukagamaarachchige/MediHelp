# Companion security review and remediation

Review date: 18 October 2026. Scope: application source, every API handler, browser authentication/authorization, upload/extraction boundaries, notification delivery, offline caching, local storage and production dependencies. Existing uncommitted UI/accessibility work was preserved. Integration testing used a separate temporary data directory; no real medication records, recipients or external messages were used.

## Findings patched

| Priority | Finding and impact | Remediation |
| --- | --- | --- |
| Critical | Next.js 14.2.35 and its PostCSS dependency had published advisories, including unauthenticated Windows-hosted server RCE. The original audit reported two vulnerable packages, with critical/high severities. Some additional advisories concern framework features this Pages Router app does not use. | Upgrade to Next.js **15.5.28**; override PostCSS to **8.5.30**; disable the unused image optimizer; pin the lockfile and restrict the tracing root to this project and exclude private data/environment files from build tracing. A build fingerprint also prevents production startup from serving stale compiled APIs after source/dependency changes. |
| High | Unauthenticated network clients could read schedules/medication lists and mark a dose taken or skipped. The caregiver UI lock did not protect the elder APIs. | Enforce server-side trusted-device enrollment on every health API. Device tokens are 256-bit random secrets in HTTP-only cookies; only their hashes are stored. Keep caregiver elevation separate so an elder can use Today without leaving Settings unlocked. |
| High | The known default `1234` and PIN-disabled profiles could expose administrative access. PIN limits were only per-process/per-IP. | Remove default-PIN login. Require first-time local setup of a 6–12 digit non-repeating PIN; migrate old plaintext PINs to scrypt. Enrollment is required even when caregiver elevation is disabled. Persist account-wide failure limits so changing IPs or restarting the server does not bypass lockout. |
| High | Push registration accepted arbitrary HTTPS endpoints, allowing the scheduler to make attacker-controlled server-side requests. Existing stored endpoints were trusted at send time. | Allow only recognized FCM/Mozilla/Apple/Windows push-service hosts over HTTPS, without credentials, custom ports or fragments. Validate P-256 and auth keys. Revalidate saved endpoints before every send, bind subscriptions to authorized devices, cap counts and enforce network timeouts. |
| High | Medication updates spread arbitrary request fields into records, and malformed names/types or images could crash handlers. Photos were validated mostly by a data-URL prefix. | Apply typed field allowlists, enums, string/count/supply limits and bounded request bodies. Validate raster signatures, dimensions and encoding; reject SVG/HTML, mismatched MIME data and oversized images. Keep immutable IDs/timestamps server-owned. Retiring a medication removes pending doses without regenerating completed slots. |
| High (safety integrity) | Missing AI keys or failed image extraction could return unrelated demo medicines with high confidence. Text fallback guessed dose and duration. | Fail closed for unconfigured/failed image extraction; normalize and bound provider output. Text fallback leaves unknown fields blank. The demo action loads clearly labeled text and never pretends to scan an arbitrary image. |
| Medium | No shared API CSRF/Host checks, limited request throttling and missing browser security headers. | Add independent API Origin/Fetch-Metadata/JSON/Host checks and bounded rate-limit maps; deny unconfigured hosts and reject repeated query parameters. Bind to loopback by default, require configured HTTPS for remote hosts, restrict trusted proxy addresses, and add CSP, anti-framing, MIME-sniffing, referrer, cross-origin and permissions policies. Authorization remains in handlers and does not rely on middleware. |
| Medium | Session rotation/revocation and response redaction were incomplete. Scheduler delivery maps exposed push endpoint capability URLs in dose JSON. | Separate persistent device and short-lived caregiver cookies; use Secure `__Host-` cookies on configured HTTPS origins. Rotate elevated tokens, revoke other devices/subscriptions on PIN changes, support explicit device removal, and allowlist public dose/medication fields so delivery capabilities never reach clients. |
| Medium | Reminder jobs could overlap, and asynchronous writes could overwrite a concurrent dose confirmation or resurrect a removed dose. | Serialize jobs within the server process, bound execution time, recheck dose/device state before sends, and merge only delivery metadata into the current store. Completed/removed doses and stock changes survive concurrent delivery. |
| Medium | Direct JSON writes could leave a truncated store after a failure. Legacy logs could contain PINs or entire uploaded photos. Data-directory configuration could accidentally expose private files under `public` or build assets. | Write to a private temporary file, fsync and atomically rename. Apply restrictive creation modes, redact secrets/photo payloads from logs, cap store size and reject publicly served data directories (including resolved symlinks). PIN migration also redacts legacy log metadata. |
| Medium | Previously opted-in offline caches could retain health snapshots after authorization was revoked; arbitrary API query strings could grow the cache. | Purge pre-enrollment caches, require an authorized device for offline opt-in, clear snapshots on authorization failures/device removal, allowlist exact API cache keys, bound cache entries/response size and retain the existing 24-hour expiry/read-only restrictions. Sync the Settings toggle with actual worker state. |

## Validation

- `npm audit` and `npm audit --omit=dev`: **0 known vulnerabilities** after remediation. This is a dependency-database result, not proof that the application or operating system has no vulnerabilities.
- Production build succeeds with Next.js 15.5.28. Unit/regression tests run using the available Node 24 runtime.
- `npm test` covers duplicate-dose idempotency and stock/timestamp integrity; device/caregiver roles; local setup forwarding rules; HTTPS cookie/transport rules; persistent cross-IP PIN lockout; CSRF/Host/body validation; mass assignment; raster content/dimension checks; push SSRF (including malicious persisted endpoints); concurrent reminder jobs; concurrent confirmation/retirement preservation; fail-closed extraction; legacy PIN migration; log redaction; and atomic-write failure preserving the original store.
- A real production server on a loopback-only test port was exercised with isolated data and browser contexts: anonymous data reads/writes denied, default PIN rejected, remote-forwarded setup rejected, local setup succeeds, forged Origin/Host requests rejected, caregiver lock preserves elder access while denying edits, PIN changes revoke a second browser and push subscriptions, completed dose retries preserve stock/time, 225% mobile text fits, offline cold reload remains read-only, and forgetting a device removes its cached health data. The page hydrates without CSP violations or browser exceptions.
- No provider messages were sent during tests. Actual push delivery, WhatsApp account configuration, production reverse-proxy/TLS settings and mobile OS behavior require deployment/device validation.
- The tracked-file/credential-pattern check found no committed `.env` credentials or local health/key files. The data store, push keys and temporary files remain ignored.

## Runtime and deployment actions

1. **Runtime fixed locally without a global change.** The machine’s default `node` was **20.19.6**, an end-of-life release. Node **24.22.0** (the current Node 24 LTS patch from the official distribution index, released 14 October 2026) was installed under `%LOCALAPPDATA%/Companion/runtimes`. Its archive and executable were verified against official SHA-256 checksums. Startup/build wrappers select this verified app-local runtime when the system runtime is unsuitable; `.nvmrc` and package engines require 24.22.0 or newer Node 24. Other machines must install a current patched Node 24 release. The system-wide Node installation was not changed. Final validation runs on Node 24.22.0.
2. Restart old app processes after the dependency upgrade. On the next local visit, a profile still using the default PIN must complete secure setup. Other custom legacy four-digit PINs remain compatible, but should be upgraded in Settings.
3. For remote access configure an HTTPS `COMPANION_ORIGIN`, preserve Host at the reverse proxy, supply `X-Forwarded-Proto: https` from a loopback or explicitly trusted proxy, and restrict direct backend access. Keep the default loopback bind unless the deployment requires otherwise. Reverse-proxy-level body/rate limits remain appropriate for volumetric attacks before application parsing.
4. Protect and back up the data directory. On Windows, POSIX creation modes do not replace NTFS ACLs or full-disk encryption. Offline browser caches are explicitly opted-in but are **not app-level encrypted**; physical access to a trusted browser/device remains a privacy risk, and a disconnected device cannot receive immediate remote revocation.
5. This remains a **single-elder, single-process** local application. Caregiver sessions live in memory; device enrollment and PIN lockout persist in the store. Multi-instance deployment requires transactional storage, shared rate/session infrastructure and a stronger identity model. A PIN is not MFA or an enterprise account system. This review is not a medical, regulatory or complete penetration-testing certification.
